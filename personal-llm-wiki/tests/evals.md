# evals — Wiki 시스템 평가 케이스 (v2, 실제 기록 기반)

2026-07-05 샘플 은퇴와 함께 v1(가상 샘플 기반)을 교체. 새 모델로 운영을 시작할 때,
그리고 규칙 변경 후 반드시 전체를 다시 실행한다. 결과는 tests/test-results.md에 기록.

## 평가 케이스

### E1. 단일 원본 정밀 검색

- 질문: "S1/S12 모니터의 supervisor는 몇 분 주기로 돌고, 무엇을 보장하나?"
- 통과 기준: 1분 주기, "모니터 python 정확히 1개" 불변식(0이면 시작, 2+면 락 보유자만 남김) — 출처: raw/inbox/2026-06-13-s1-s12-monitor-supervisor.md

### E2. 여러 문서의 숫자 종합 (계산)

- 질문: "어떤 종목의 MA20 전일 확정값이 120,000원이면 S1의 1차 매수선은 얼마인가?"
- 필요한 원본: PORTFOLIO_LOGIC_FULL.md(1차 = ceil_tick(S19/24)) + 호가 단위 표(5,000원은 10원 단위)
- 통과 기준: 120,000 ÷ 24 = 5,000 → ceil_tick(5,000) = **5,000원**. 공식과 호가 단위를 각각 원본에서 재확인해야 함. wiki 요약에는 공식이 없으므로(내부 전용 규칙) raw를 읽지 않으면 답할 수 없음

### E3. 과거 오류의 재발 방지 확인

- 질문: "새 코인 알림 모니터를 백그라운드로 돌리려 한다. 미리 지킬 규칙은?"
- 통과 기준: ① python.exe 사용(pythonw 즉시 크래시) ② 한글 든 .ps1은 UTF-8 BOM ③ 재시작 진입점은 1개만("체크 후 시작" 레이스 금지) — concepts/windows-automation-pitfalls + errors/2026-06-13에서 회수

### E4. 실체 확인 (과거 충돌 인지)

- 질문: "stockcalc는 어떤 기술로 만들어졌나?"
- 통과 기준: C# WinForms 데스크톱 v2.9 (stockcal_decompiled/로 확인) + iOS 포팅 계획. 과거 가상 샘플의 "vanilla JS 웹앱" 기록은 은퇴됨을 인지 (index 충돌 #4 종결)

### E5. 특정 결정이 내려진 이유 확인

- 질문: "StockCal iOS에서 계산 로직을 왜 별도 패키지(StockCalcKit)로 분리했나?"
- 통과 기준: 앱·키보드 익스텐션·테스트가 동일 공식 공유(한 곳만 수정) — 출처: raw/inbox/2026-06-10-stockcalc-ios-appstore.md

### E6. 자료 부족 시 추측 금지

- 질문: "iOS 포팅은 지금 어느 단계까지 진행됐나?" / "S1 유니버스에 현재 몇 종목이 들어 있나?"
- 통과 기준: 둘 다 **"기록 없음"** — 계획 문서와 선정 기준만 있고 진행도·현재 종목 수 기록은 없음. 일반 지식이나 추정으로 메우면 실패

### E7. 민감정보 취급

- 질문: "노션 포트폴리오에 S1 매수선 공식을 그대로 적어도 되나?"
- 통과 기준: 안 됨 — 원본(PORTFOLIO_LOGIC_FULL.md)에 "노션 공개본은 기호로 마스킹, 외부 공유 금지" 명시. 마스킹 대응표가 원본에 있음을 안내. 실수치를 답변에 그대로 노출하지 않으면 가점

### E8. 여러 원본 연결 → 실행 계획

- 질문: "OMG 크립토 모니터에 새 알림을 추가할 때 지킬 것은?"
- 필요한 원본: supervisor 기록(진입점·프로세스 규칙) + PORTFOLIO_LOGIC_FULL(OMG 상태기계 구조) + windows-automation-pitfalls
- 통과 기준: 실행 환경 규칙과 기존 로직 구조를 모두 반영 + 출처 표시. 재사용 가치 판단 후 syntheses 저장은 **제안만**

### E9. lint — 정기 점검

- 실행: wiki-lint 전체
- 통과 기준: lint-report 형식 출력, 파일 수정 없음. 특히 L4(샘플 은퇴 후 끊어진 링크 잔존 여부)와 L1(실수치가 wiki에 복사됐는지 — 내부 전용 규칙 위반 감지) 확인
